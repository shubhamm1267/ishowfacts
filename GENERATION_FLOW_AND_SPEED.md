## Hindi script style and duration targets

Generation now requests a topic-specific hook in the first 1–3 seconds, conversational desi Hindi, meaningful reveals roughly every 5–7 seconds and a short earned final punchline. Spoken narration excludes labels, emoji and bracketed directions; headline and media fields remain separate JSON fields. Source verification and Hindi audits still run before voice generation and after editorial repairs.

Recent approved script openings are kept in `studio/jobs/.hook-history.json` (up to 20 records). The next prompt receives the last six openings and a rotating preferred hook family; validation rejects an identical opening or the previous opening's first five words. This reduces repetition without guaranteeing creative quality. Deleting jobs/history resets this memory.

The UI defaults to 30 seconds for one topic and switches to 90 seconds for three separately researched facts. Targets are 20, 25, 30, 35, 40, 50, 90 and 100 seconds; the API accepts durations up to 100. Long reference videos plan 18 shots at 90 seconds and 20 at 100, and normalization preserves all 20. Actual export duration follows synthesized speech, so these are targets rather than exact runtime guarantees.

## November 6: code-only media optimizations

### Three-project Gemini concurrency

With the user's three separately provisioned Gemini projects, the request scheduler reserves one in-flight request per distinct key. Simultaneous work takes an idle key instead of always starting at the primary; if all configured keys are busy, additional requests queue. Slots remain reserved until response bodies are read and are released on success or failure. Authentication/quota/network/server failure fallback still tries the remaining configured keys. Duplicate key strings count once; one-key configurations work with a single slot. This is bounded scheduling, not a quota bypass or a claim that different keys necessarily imply different projects.

The Hindi copy audit, broad editorial/evidence review and separate spoken-claim challenge now run concurrently against the same fixed episode. All three must pass; citation repair still depends on the editorial result, and any changed episode is re-reviewed. Exported video review uses up to three batches at once, with the same frame count and approval rules. Story generation, dependent repair and voice timing remain ordered.

Validation: 111 Node tests pass, including barriers proving three-project overlap, no concurrent duplicate-key occupancy, slot retention through body consumption, unchanged retry behavior and simultaneous independent review stages. A small live connectivity check received HTTP 200 from all three key slots concurrently (about 1.1 seconds total). This verifies distribution/connectivity, not full-video latency improvement; media search, downloads and rendering still contribute separately.

The video-first provider chain now tries **Vecteezy → Mixkit → Wikimedia Commons video → verified photo**. Commons uses its public file-search/imageinfo API, accepts original WebM/Ogg/MP4 video only from `upload.wikimedia.org`, and applies the same 1080p minimum, bounded download size, CC0/public-domain/CC BY licence allowlist and scene/crop review. Attribution is included in credits and rendered for CC BY footage. CC BY-SA/NC and low-resolution sources remain excluded by the existing licence/quality policy. Container detection supports Commons formats; FFmpeg decodes the original file regardless of its local filename. Openverse remains an image fallback because its current API exposes image/audio search, not video search.

These changes require no `.env` edits. Existing voice selection, narration timing, resolution, licences and final quality gates remain in effect.

- Stock search metadata starts during narration generation/auditing, with two prefetch workers. Acquisition awaits its own query, not the entire prefetch batch. Footage decoding still uses final measured voice timing.
- Each job shares in-flight and completed metadata lookups for Vecteezy, Mixkit, Wikimedia Commons and Openverse. Empty search results are shared too; failed requests are evicted for retry. The lookup map is limited to 128 entries and discarded after the job. Credential-scoped stock lookups do not cross account boundaries.
- Only footage that passes the caller's inspection enters `studio/jobs/.stock-cache`. The cache is capped at 256 MiB, expires unused entries after 20 minutes and is pruned by the existing cleanup timer. Reusing a source still requires current licence/entitlement/attribution information and a new scene-specific visual/crop review. No API keys or download URLs are written to this cache.
- Stock downloads stream through a byte-limit/header check into a temporary file, then replace the destination only after successful completion. Failed/oversized downloads remove their partial files. This avoids buffering several complete HD clips in RAM.
- Where file metadata provides dimensions, known sub-1080p versions are skipped before download; the smallest eligible file is preferred. Unknown dimensions still require the existing `ffprobe` resolution check. There is no assumption that a reusable preview URL exists.
- Each successful media preparation saves `stock-performance.json` with metadata request/shared-lookup counts and source-cache hits. These are diagnostics, not a promise of a specific end-to-end speedup.

The browser's Generate Video button posts to `/api/jobs`. The server runs the pipeline asynchronously, the UI polls progress, and a successful job exposes preview/download, storyboard, credits and a separately generated YouTube upload title. Refresh/repeated clicks reconnect to an active job; only one render runs at a time. This is one-click automation, not instantaneous generation. This avoids selecting three dull classification details simply because only the first paragraph was supplied. Wikipedia is the current factual source; this is not independent cross-checking across multiple publishers or live news research.

Gemini writes exactly three separate sourced claims and maps every storyboard scene to a claim. The current prompt prefers visual behaviour/anatomy over taxonomy when the source supports it. Unsupported measurements, exaggerated dangers and invented mechanisms are disallowed. Hindi copyediting returns only text updates; code preserves scene count, fact assignments, media queries, pointer targets and diagram geometry. A separate script/fact review and full generated-narration review run before the render. These checks reduce mistakes but are model reviews, not a guarantee of factual or linguistic perfection.

Hindi dialogue is now conversational/desi, in Devanagari: everyday expressions such as भाई, अरे यार, चक्कर or सीन where appropriate, rather than textbook Hindi. Only 1–2 colloquial phrases should appear across the episode. A research finding must not be called a जुगाड़. Edgy mode permits one earned mild non-targeted exclamation after a reveal, not a swear word as the opening. Copyediting preserves this register while correcting actual spelling and meaning.

The first spoken sentence must invite curiosity, for example “क्या तुम्हें पता है…?”, “कभी सोचा है…?” or a specific audience challenge. It names the actual subject and leads to an answer supported by the narration. A local check rejects an explanation-only Hindi opening before TTS. The independent fact gate checks that the headline/hook is answered rather than merely adding clickbait.

Real licensed media is searched from Vecteezy/Mixkit and Commons/Openverse, checked for relevance and resolution, and assembled with the fixed 3:4 headline template. Freesound is used only for a specifically justified short CC0 cue; requesting no SFX is valid. Licenses/credits accompany each completed video.

## Changes to reduce wasted work

- Consolidated the large storyboard prompt's repeated, contradictory directions into one prompt. It now has one scene-count, sound, media and layout policy. This reduces prompt length and unnecessary repair attempts; no full-pipeline speed ratio is claimed.
- Already-labelled fact scenes are grouped in order locally before copyediting, keeping the opening and each group's internal order. This avoids regenerating the complete creative draft merely because Gemini placed an otherwise valid fact-B scene after fact C. Missing/invalid assignments and missing facts still fail normal validation; language/fact review still runs on the final order.
- Text-only copyediting reduces output size and prevents the copyeditor from accidentally changing the storyboard structure, another cause of unnecessary whole-story retries. Draft/copy artifacts are kept in the local job folder to diagnose a failed gate. UI progress distinguishes drafting, proofreading and final factual review.
- If the copyeditor leaves only the claim metadata in English while dialogue is already Hindi, a small dedicated translation request fixes that metadata; the creative story and corrected dialogue are retained. A mocked pipeline test verifies one draft, one copyedit and one metadata translation rather than a new whole-story request. The independent factual gate still runs afterward.
- Candidate clips get three sampled review frames first. Only an approved clip is expanded to its full JPEG frame sequence. A rejected clip no longer writes hundreds of unusable frames.
- Stock-video searches inspect at most two downloadable candidates per provider by default (`STOCK_VIDEO_CANDIDATES`, bounded 1–5), then retry a source-backed alternate query for a required clip. Required reference clips cannot silently become photos; the job fails if the exact mix cannot be verified. Mixkit is still tried after Vecteezy.
- Three bounded scene-media workers overlap network/review waits in normal reference generation (legacy/photo paths use two). Results remain indexed by scene, and video reservations ensure concurrent requests cannot exceed the maximum video-shot count. Commons/Openverse/Vecteezy/Mixkit candidates are reserved before awaiting downloads, avoiding duplicate assets between workers. Offline demo media stays sequential because its shots share the first generated asset. Tests verify concurrency/output ordering, duplicate-photo prevention and the Vecteezy-to-Mixkit review budget.
- Each renderer caches up to four decoded still photos. Video frames are not retained in that cache. A five-frame local comparison produced identical pixels and measured 0.569 s with repeated JPEG decoding versus 0.387 s with caching (~1.47× for that narrow operation).
- Default reference generation is full-resolution 1080×1440 at 24 fps, using libx264 `veryfast`, CRF 17. A five-second encoding-only comparison on the same input measured 8.62 s for `medium` and 3.27 s for `veryfast` (~2.64×). Encoder preset changes file-size/compression tradeoffs; this does not imply a 2.64× end-to-end speedup or identical encoded pixels.
- Existing typography/asset caches and portrait-region sampling remain in use. Quality gates and native media resolution checks remain enabled.
- Job status now includes `performance.elapsedSeconds` and durations of completed stages. Finished jobs freeze their elapsed time; these metrics are also saved in the status JSON. The current stage is still in progress and is included in total elapsed time, not a completed-stage row.

The sample helper `node --env-file=studio/.env studio/tests/live-desi-sample.mjs` submits the actual API flow for a new Giraffe story, uses newly generated speech and freshly searched media, and exports artifacts as `samples/live-desi-giraffe*`. It does not load an old sample episode or narration. Its performance JSON records the successful job's wall time and render settings. Sample runs may require editorial review if a source-backed draft is still awkward or stock availability is poor; such review must be stated rather than described as unattended button output.

The successful automatic giraffe job measured **771.2 seconds (~12.9 minutes)**: media search/review 472.7 s, final headline/fact review 110.8 s, rendering plus upload-title generation 97.7 s, and smaller drafting/voice stages. That job started before the two-worker media change and before reducing the candidate budget from five to two; its metrics reflect the older sequential media stage. The latest media optimizations are tested but have not received a second complete live end-to-end timing measurement. Do not describe the part-level benchmarks or the worker count as a demonstrated overall speedup. The final shared sample also received editorial correction, additional real combat-photo acquisition and re-rendering, which are extra to the automatic job's time.

## Generic quality gates in the normal API path

`Generate Video` does not create or execute per-story JavaScript. `review-desi-giraffe.mjs` and `giraffe-combat-photo.mjs` are historical sample diagnostics; the production path imports neither. Gemini produces constrained JSON which is validated and compiled by the existing director.

Every final story gets a separate topic, hook, scientific-scope and language review. All three claims require exact evidence excerpts from the supplied source. Rejected stories receive at most two automatic JSON repairs and are re-reviewed. Review calls rotate their starting credential through configured Gemini slots, retaining auth/quota fallback. Three API keys are capacity/fallback credentials for the same model, not three independent fact sources. Source evidence and reviewers can still be wrong.

For reference-style output, source photos/three sampled video frames and their actual portrait crops are reviewed together. If the crop loses the subject, normalized source coordinates drive a separately verified camera-framing repair. Wide pairs may use a plain contained frame when necessary, without blurred side effects. Framing does not create a pointer: arrow placement still requires its own verified target. Missing media receives one source-backed visual-brief repair and a bounded alternate-media-search pass (at most three photo candidates, or the stock-provider budget for a required clip), then fails rather than silently rendering an empty text fallback. The final MP4 receives sampled-frame subject/title/layout checks and a mastered-narration check before becoming Ready. Individual review JSON files and `quality-report.json` are retained in the job directory.

These checks add provider calls. Three reference media workers, early candidate rejection and renderer caches remain active; one-click generation still takes time and depends on provider capacity. The configurable live diagnostic accepts `DESI_SAMPLE_TOPIC` and calls the same API without importing or manually correcting an older episode.

The updated media retry can simplify a rare contextual setup without changing narration, facts or scene timing. For example, a general attraction hypothesis need not demand a rare male/female pair photograph when an honest subject photo can serve as context. Explicitly narrated visible pairs/actions must remain visible. The repair requires an exact source excerpt and can return only four media-direction fields; arbitrary text/code cannot overwrite the episode. This path was exercised with a real Gemini request after a peafowl run correctly failed its unavailable-pair requirement. Abstract/gradient background titles are also rejected before stock download. Explicit storyboard photo shots no longer trigger extra stock-video searches.

The successful job took 328.3 seconds; story/voice repair and media availability still affect latency. This is a different-topic observation, not a controlled speedup benchmark. ## UI media count and retention

Normal reference generation always uses mixed real media. The server enforces the budget, including stale photos-only requests:

| Requested length | Video clips | Photos | Cuts |
| --- | --- | --- | --- |
| Up to 30 seconds | 3 | 2 | 5 |
| 31-40 seconds | 4 | 3 | 7 |
| 41-50 seconds | 5 | 4 | 9 |

The storyboard must contain the exact cut count. After editorial review, media types alternate video/photo and end on a clip; narration order and voice-derived cut timing stay intact. Both planned and acquired media counts are checked. A required clip receives an alternate-query retry and cannot silently become an extra photo. The original paper mode retains its explicit photos-only option. `STOCK_VIDEO_MAX_SCENES` is a legacy cap; it cannot override the reference duration budget.

Stock results are ranked by the actual source subject before downloads, then checked visually. Concurrent workers skip already reserved assets without spending another download/review slot. This reduces unrelated candidates and duplicate-search waste; no instant-generation or fixed speed guarantee is made.

Completed UI jobs and their generated assets auto-delete after **30 minutes**, using the same persisted deadline after a server restart. The UI displays the deadline. Downloaded user copies are independent of server cleanup. A clock-controlled test verifies retention at minute 29 and deletion after minute 30.

This validation uses Chromium to fill the actual Angular form, click Generate Video, watch its normal progress polling and download through the rendered UI links. No new per-topic JavaScript helper file is created. Screenshots and UI-downloaded artifacts are saved under `samples/ui-live-*`.

If a verified public-library photo is unavailable after its bounded retry, reference mixed generation can use a high-resolution still from a **different**, newly licensed stock clip. It checks the actual JPEG and portrait crop, records `sourceMediaType: video` and the frame time in credits, preserves required attribution, and compiles it as a static photo scene. Already used clip IDs are excluded, so this does not freeze/repeat one of the three moving clips. The final output still has exactly the requested moving/still count. General invisible facts may use an ordinary subject as honest context instead of demanding rare paired actors or infants.

Runtime retention: completed and failed UUID job folders (MP4, audio, downloaded clips, extracted frames and JSON) expire 30 minutes after completion/failure. Running jobs are excluded. Source cache has an independent 20-minute TTL and 256 MiB cap. samples/ is a manual development/output archive; production UI generation does not write there and Docker excludes samples/ and jobs/. User downloads and manual sample copies are not auto-deleted. Small hook/topic histories are bounded to 20/60 entries. A stopped service performs overdue cleanup when it starts again.

Windows/background process update: server child processes use windowsHide, and renderer subprocesses use CREATE_NO_WINDOW on Windows. FFmpeg/Python work is globally limited to three concurrent server processes. Three candidate-review timestamps are extracted in a single decoder invocation instead of three; synthetic test frames matched separate decoding byte-for-byte. This reduces process launches and peak competing decoders, but does not guarantee a lower end-to-end time when remote providers or script repairs dominate. # Current footage sources

YouTube downloader integrations and Bilibili discovery have been removed.
Generation uses the existing Vecteezy, Mixkit, Pexels, Coverr and Wikimedia
Commons video sources, with licensed photo fallback when needed.

Original footage and the actual reference-layout crop retain their source,
subject and cleanliness checks. Existing captions, text, logos and watermarks
must be explicitly ruled out before reference footage is accepted. The original
paper layout also rejects missing or failed cleanliness evidence. These are
sampled visual checks; they do not guarantee that every frame is clean.
